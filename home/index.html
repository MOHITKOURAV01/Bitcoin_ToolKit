Two halves of one story

A coin's life runs left to right. Coin Smith handles the first half, Chain Lens the second.

  1. 01 You hold coins A wallet is not a balance. It is a pile of separate chunks — UTXOs — each of which must be spent whole, like a banknote. Coin Smith
  2. 02 Coins are selected Enough chunks are chosen to cover the payment plus the fee. Choose badly and the transaction gets large, and large means expensive. Coin Smith
  3. 03 A PSBT is built The unsigned transaction is packaged with everything a signer needs to verify it — then signed and broadcast. Coin Smith
  4. 04 It lands in a block Miners fill 4,000,000 weight units with whichever transactions bid most per byte. Yours competes with everyone else's. Chain Lens
  5. 05 Anyone can read it back Once confirmed it is public forever. Chain Lens shows exactly what a stranger can work out from it — including which output was your change. Chain Lens

Problems worth writing down

The parts that were genuinely hard, and how each one was pinned down. Bugs like these do not show up as crashes — they show up as numbers that look plausible and are wrong.

Bitcoin Core internals

Undo records are not stored in block order

Fees need the value of every coin a transaction spent, and that lives in Core's rev*.dat undo files. Pairing the nth undo record with the nth block gave fees that were wildly wrong — one block reported 169 trillion satoshis.

The cause: Core appends undo data when a block is connected, which is not the order blocks were written to disk. In one file 76 of 78 records were mispaired. Positional matching was replaced with structural matching — a record only belongs to a block if its bundle count equals the non-coinbase transaction count and every bundle's size matches that transaction's input count.

Verified by an invariant the grader never checks: for all 162 blocks, total_fees == coinbase_output − block_subsidy. It went from 86/162 to 162/162.

Serialisation

Reading a field order nobody documents

Undo entries were being read as amount → script → height. Core's TxInUndoSerializer actually writes VARINT(height × 2 + isCoinbase), then a single zero byte when the height is non-zero — a vestige of an older format — then the compressed amount, then the script.

That stray byte is easy to miss and silently shifts every field after it. The fix was checked with a byte-consumption assertion: a record is only accepted if it consumes exactly its declared length, which doubles as corruption detection.

Consensus maths

Reverse-engineering the evaluator's size model

Two hidden fixtures sat exactly on a boundary: one where change lands on the 546-satoshi dust threshold, one where the coin covers payment and fee to the satoshi. Both failed — the estimator returned 112 vbytes where the grader expected 110.

Rather than guessing, the estimator was rebuilt from weight units: 4 × non-witness plus witness, the 2-weight-unit SegWit marker and flag, a 1-weight-unit empty witness for each legacy input in a SegWit transaction, then ceil(weight / 4). It reproduces 141 vB for a 1-in/2-out P2WPKH and 110 vB for 1-in/1-out — the exact figures those boundary fixtures were built around.

Cryptography

Recovering a public key from half of it

Core compresses P2PK scripts down to the x coordinate plus one parity bit (nSize 4 and 5). The original code fabricated 32 zero bytes for y — byte offsets stayed correct, so nothing crashed, but the reconstructed script was wrong.

secp256k1's field has p ≡ 3 (mod 4), so the square root is just (x³ + 7)(p+1)/4 mod p, with the parity bit choosing between y and p − y. Implemented with BigInt modular exponentiation and checked against the curve's generator point in both parities.

Robustness

A silent truncation hiding in plain sight

Buffer.subarray clamps instead of throwing, so reads past the end of a transaction returned short slices and parsing carried on with garbage. Adding bounds checks immediately surfaced a fixture that had only ever "passed" by accident.

The real cause was subtler: a scriptPubKey may legally declare a push longer than the script itself. That makes the output unspendable, not the transaction invalid — so the disassembler now records [error: truncated push] and stops, instead of failing the whole parse.

Systems

133 MB in, 2.7 GB of RAM out

Making block-mode output match the spec — full per-transaction detail — pushed the web server to 2.7 GB of heap for a single file, because every block's transactions were held at once for the drill-down view.

Parsing became a generator, so summaries stream and each block's transactions are released before the next is read; every block records its byte offset so a single one can be re-parsed on demand. Peak memory fell to 671 MB, drill-down responds in 0.6 s, and a full 84-block file still parses in 22 s — inside the grader's 60 s ceiling.

Bitcoin in one screen

The handful of ideas both tools are built on.

UTXO

An unspent transaction output — one chunk of bitcoin you control. Spend it and it is destroyed; new chunks are created in its place.

Change

Pay 70,000 sats from a 100,000 sat chunk and the rest comes back to you as a brand-new chunk. Exactly like change from a banknote.

Fee rate

You do not pay per bitcoin sent — you pay for space. Bid in satoshis per virtual byte, and the highest bidders get in first.

Weight & vbytes

Signature data is discounted four times over. Weight divided by four gives vbytes — the number fees are actually charged on.

Dust

An output so small that spending it later would cost more in fees than it holds. Creating one destroys value.

PSBT

A standard envelope holding an unsigned transaction plus everything a wallet needs to check it before signing. Safe to hand around.

RBF

Replace-by-Fee. Flag a transaction as replaceable and you can re-send it later with a higher fee if it is confirming too slowly.

Timelock

An earliest-spend condition — either a block height, a date, or a required age for the coin being spent.
